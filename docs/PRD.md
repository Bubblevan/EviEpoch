# EviEpoch 参赛产品需求文档（PRD）

**版本：** 1.0 目标设计  
**日期：** 2026-10-27  
**参赛方向：** Agent Memory Challenge / Textual / Open-source Methods  
**配套：** [技术设计](TECHNICAL_DESIGN.md) · [赛事与实现上下文](COMPETITION_CONTEXT.md)

## 1. 产品定义与目标

EviEpoch 是具备巩固、关系推理、可信修订和生命周期治理的长期文本记忆服务。它将用户跨会话信息组织成可追溯的来源、事实、事件、情景、偏好和规则，在查询时为平台统一 Answer 提供时间一致、来源明确、覆盖全部必要前提的证据集合。

正式竞争目标是争夺文本开源方法榜第一，并形成可复现的方法贡献。产品以完整能力设计，不按当前实现体量、研发难度或剩余时间裁剪核心机制。当前代码是实验起点，本文定义实际参赛产品的目标行为。

顶层研究问题来自 Du 综述的第 10 章：如何巩固而不丢关键事实、按因果而不只按相似度检索、反思而不固化错误、安全遗忘。时间状态与完整证据检索贯穿四题，不单独代表产品的全部目标。完整依据见 [研究议程](../literature/survey-agenda.md)。

## 3. 使用者和交付边界

| 使用者 | 需要完成的事 | 产品交付 |
|---|---|---|
| AML 评测运行器 | 增量写入、重试、跨会话检索 | 同步 Add、隔离 Search、稳定 ID 与正确响应 |
| 平台固定 Answer | 从证据正确回答事实、时间、关系、规则和个性化问题 | 有序、充分、来源可核验、未被无关信息淹没的原始证据 |
| 项目研究者 | 检查记忆形成、修订、巩固、取证和遗忘 | 公开数据 Workbench、操作 diff、路径和消融报告 |
| 赛事复核者 | 对照成绩与方法/运行版本 | 固定 commit/镜像/模型/提示词/配置与来源披露 |

对外产品是记忆 API。答案生成由赛事平台执行；内部推理的产物是检索计划、状态假设和证据 ID。官方合同约束、模型、截止与数据责任集中在 [赛事上下文](COMPETITION_CONTEXT.md)。

## 4. 完整能力范围

### 4.1 分层巩固与持久来源

保存源内容、原始 role、时间和会话顺序；从来源形成原子事实、事件、关系及可复用情景、画像/规则。各层保留源片段链接。新记忆通过双缓冲质量检查、实体/时间对齐和重要性估计后进入长期组织；每一层均可回钻。

巩固的目标是提高检索密度并减少工作上下文负担。罕见但关键的否定、数量、日期、约束、过敏/健康和例外信息需要明确保护与验证。晋升和压缩不能使原始支持失去可恢复性。

### 4.2 时间状态、因果与规则依赖

区分记录时间、陈述时间、事件时间和有效时间；支持当前值、指定历史时点、区间、事件顺序、变化链与比较。明确区分真实变化、过去陈述被纠正、未来计划、不同主体和不同适用条件。

将因果支持、操作前提、规则、例外和约束建成有来源的依赖关系。why/order/procedure 问题必须召回必要上游证据，包含语义相距较远的原因或规则。

### 4.3 可信反思与修订

从多条经历形成摘要、模式和经验时，记录其证据、适用域、置信度和反例。控制器主动搜索能否定高影响结论的来源，依据支持/反证修订状态。未验证经验和源陈述使用不同类型，访问频繁不等于真实。

Search 问句、答案选项、模型自己的回答不能变成用户事实。新事实写入与经验修订必须能指向已提交 Add 来源或公开实验的合法验证资料。

### 4.4 问题驱动的完整证据集合

将问题解析为实体、属性、时间、来源和必要前提组成的需求图。通过语义、词法、时间、关系和层级记忆发现候选；联合选择能满足需求图的来源集合。对缺失前提继续取证，对真正冲突保留可解释的替代证据。

最终输出原始证据、真实时间与稳定 ID。内部摘要、图或反思可以影响选取，但不能无来源地生成“记忆事实”供 Answer 采信。

### 4.5 安全遗忘与治理

将活跃度衰减、事实版本失效、禁止检索和物理擦除分为不同操作。明确忘记请求作用于目标范围及原文、事实、摘要、图、词法/向量、缓存与重放副本；正常历史更新仍保留历史可查询性。

每次检索都服从当前治理状态。历史查询不能复活已禁止披露的内容；新知识的明确重新提供按新的来源与政策处理。

### 4.6 偏好与程序记忆

偏好包含主体、时间、情景和例外，避免将局部选择固化为全局画像。程序记忆包含规则、前置条件、步骤、例外、结果和适用范围；Search 提供执行所需证据，帮助固定 Answer 完成 G 维度任务。它与普通事实共享来源合同，具有独立组织与查询计划。

## 5. 功能需求与验收

以下均为目标版本核心需求；依赖顺序不表示删减范围。

| ID | 功能 | 可检查的完成条件 |
|---|---|---|
| F01 | 来源保真 | 原始文字/role/时间/消息顺序可恢复；展示处理不修改权威来源 |
| F02 | 可追溯抽取 | 每个事实/事件/规则存在可定位源片段，抽取引用与原文一致 |
| F03 | 实体与关系 | 同名异人、代词、角色与属性多值/单值分别处理 |
| F04 | 多时间语义 | 事件时间与写入时间分开；不完整时间保留精度与不确定性 |
| F05 | 状态修订 | 支持、变化、纠正、冲突、计划和否定有明确语义，历史可恢复 |
| F06 | 巩固 | hot/long-term/summary 层有晋升条件、来源覆盖、关键事实保护和回钻 |
| F07 | 可信反思 | 经验可被反例挑战；修订有来源、适用域和置信度变化记录 |
| F08 | 遗忘治理 | suppression/erase 对全部派生链生效，重试与缓存不复活目标 |
| F09 | 查询需求图 | 同一问题可表达多个实体/时间/前提和替代状态假设 |
| F10 | 混合关系检索 | 原文、派生索引、词法、向量、时间与关系路径共同参与候选发现 |
| F11 | 证据集合优化 | 优化覆盖、依赖、时间/来源一致性与预算；能对缺失前提迭代取证 |
| F12 | 原文证据交付 | 输出来源可定位、ID 稳定、相关性有序、数量和 token 预算合法 |
| F13 | Streaming 一致性 | Add 成功后的 Search 看到新一代状态；旧缓存不会隐藏新增/删除 |
| F14 | 隔离与认识论边界 | 无跨 user 记忆；选项不作事实；不足证据不被包装成肯定结论 |
| F15 | 研究 Workbench | 公开样本可看来源图、状态 diff、控制动作、因果路径和失败归因 |
| F16 | 规模化运行 | 真实模型/公网链路下记录吞吐、尾延迟、成本、续跑与数据保留 |
| F17 | 可复现发布 | commit、镜像、schema、模型、prompt、reranker、配置和数据协议绑定 |

## 6. 核心验收场景

| 场景 | 输入变化/问题 | 正确记忆行为 |
|---|---|---|
| 地址更新 | 2022 住 X，2024 搬到 Y；问现在/2022/变化 | 按查询时间取证，保留变化来源，不混淆时间 |
| 纠正与真实变化 | “之前说错了”与“今天搬家” | 纠正可影响旧陈述真值；真实变化保留旧值历史有效性 |
| 未来计划 | “明年准备搬到 Z” | 计划不覆盖已发生当前状态 |
| 原因远距离 | 故障描述与几个月前的配置决策语义不同 | 取回有来源的上游因果/决策证据 |
| 规则与例外 | 通常流程有例外，且规则后来修订 | 提交规则版本、适用条件、例外与相关事实 |
| 错误经验 | 形成“方案 A 总失败”的经验，后来有反例 | 限定/修订经验，反例进入支持链 |
| 关键罕见事实 | 长历史中只有一次过敏/否定约束 | 巩固后仍可完整回钻和召回 |
| 多实体多跳 | 两个同名人、多个事件才能回答 | 实体不混并，必要路径全部有源 |
| 明确遗忘 | 忘记旧地址后问旧地址 | 各层与缓存不披露被禁止内容 |
| 增量检索 | 相同问题在多个 Streaming 节点查询 | 只使用当时已提交来源；新证据改变可见状态 |
| 无答案/假选项 | 历史没有相关事实或选项含错误前提 | 不因选项/模型猜测生成记忆 |
| 个性化情景 | 某场景偏好改变但其他场景未变 | 保留适用范围，避免全局化或刻板推断 |

上述场景需同时检查检索证据和固定 Answer 的最终表现。

## 7. 成功指标

### 7.1 竞赛与研究结果

正式目标为 Cycle 2 文本开源榜争夺第一，重点形成 C/D 与因果/程序证据方面的优势。历史 45.06/58.02 是背景参照，不用作跨周期成功阈值。

本地冻结公开评测的产品目标如下；它们是目标值，当前尚未实测：

| 指标 | 目标 |
|---|---|
| 同模型/同 Answer 的本地宏平均任务正确率 | 比强 Hybrid 基线提高 ≥5 个百分点 |
| C 时间、D 治理切片 | 各提高 ≥10 个百分点 |
| B 多跳、G 规则/执行证据任务 | 各提高 ≥8 个百分点 |
| A/E/H | 相较强基线无超过 1 个百分点的退化，报告配对区间 |
| 必要证据组完整率 | 控制场景 ≥95%，自然公开数据报告分层结果 |
| 可定位来源有效率 | 100%；无来源输出为 0 |
| 关键事实巩固后可恢复率 | 已标注关键事实 100% |
| 控制集删除泄漏/跨 user 返回 | 0 |
| 错误经验被反证修正 | 报告修正率、需要的新观察数与错误传播率 |

不能用 Recall 的提升替代任务正确率，不能将不同基准的原论文最高分合成 EviEpoch 预测分。

### 7.2 系统目标

目标工作负载包括约 300M 全局来源 tokens 的完整导入，单 user 长历史及 Streaming，容量目标为 64 个并发 Add 与 256 个并发 Search。普通文本、超长来源和高集中用户分别测量；正式并发声明与真实端到端测量绑定。

延迟目标：普通 Add p95 ≤10s；事实检索 p95 ≤3s；组合/时间问题 p95 ≤10s；深层原因/全局综合 p95 ≤30s。固定工作负载下服务成功率目标 ≥99.9%。模型/API 和数据分布写入报告，不能以 fake provider 容量替代实测。

- 完整参赛 Add/Search 服务与部署资产。

- 公开开发/密封测试集清单、同条件基线、组件消融与交互实验。

## 10. 方法贡献的表达

拟提交的方法主张为：**在可追溯记忆生命周期上，将查询条件化状态/依赖推理与来源证据集合规划联合起来，并通过反证修订与保真巩固/遗忘提升长期任务表现。**

多路检索、层级图、置信度、Postgres/向量库都是实现组成和既有机制。技术报告应给出每个主张的对应实验、失败归因和适用边界。用户/问题无需知道这些实现细节；外部只观察到及时写入和更有用、可靠的证据。
