# 综述 bad case ↔ 研究论文方法对照

**基准场景来源：** Du, *Memory for Autonomous LLM Agents*, §7.3 “Staleness, contradictions, and drift”，见 [本地 PDF](<original/Memory for Autonomous LLM Agents - Mechanisms, Evaluation, and Emerging Frontiers.pdf>)。  
**证据等级：** 综述中的生日卡/旧地址是说明性 bad case；下表讨论论文机制与该例的结构对应，不表示论文在这个具体 case 上做过实验。

**阅读范围更新：** 本文只分析 §7.3 的说明性案例。综述 §8、§9 十项开放挑战和 §10 四个核心研究问题已在 [完整研究议程](survey-agenda.md) 逐项展开；项目目标以该议程为主。

## 1. 经典 bad case

综述描述：个人助手要给用户寄生日卡，却把卡片寄给用户的前任，并且用了旧地址；记忆系统不能区分 2024 年的地址与 2022 年的地址。作者提出需要时间版本、来源归因（用户直接陈述优先于 Agent 推断）、矛盾检测和周期性整理。

它至少包含四个独立子问题：

1. **当前状态：** “现在寄到哪里？”不能仅凭语义相似检索到任意一个地址。
2. **历史状态：** 询问 2022 年地址时，旧值仍应可找回。
3. **证据来源：** 用户明确陈述、Agent 推断、外部资料或抽取噪声不能等权。
4. **行动门槛：** 若最近的用户证据不明确，系统不能把“最高分候选”直接当作安全的当前地址。

“把新值放到第一位”“检测到两个字符串冲突”“召回包含地址的聊天”分别只覆盖其中一部分。

## 2. 论文是否提供了解法？

| 论文 | 对场景有用的机制 | 能解决到哪一步 | 论文证据与缺口 |
|---|---|---|---|
| **APEX-MEM** | 追加式事件与事实；有效期、置信度、证据出处；查询时按时间做 GraphSQL | 最直接覆盖当前/历史值选择、保留演变证据 | GraphSQL 消融显著改善 Temporal；没有 append-only vs overwrite 对照，也没有来源等级/寄送动作安全实验 |
| **PreCoMem** | 原始 episode 不可变；belief/hypothesis 状态与置信度；可靠性门控下 MAINTAIN / PROFILE / CORRECT | 最接近区分真实搬家与抽取噪声/弱冲突 | 变化与可靠性门控有相关消融；不是显式地址有效期数据库，未直接验证 as-of 历史地址与来源优先规则 |
| **MemoTime** | 问题时间算子解析、时间知识图谱、约束路径和事件排序 | 有助于把“现在/2022/搬家前后”转成不同查询计划 | MultiTQ 中移除 temporal evidence retrieval 后大幅掉分；评测不是用户事实 Add/冲突管理 |
| **ReFind** | 不改写原始聊天；BM25、session-RRF、邻域扩展、按时间缩小、多轮搜索 | 能找回含地址的原文、比较会话时间；提供无需重型写入的强 Search 对照 | LongMemEval 与事实更新任务成绩支持在线检索价值；没有显式 validity interval、来源优先级或保证 current-state 投影 |
| **MemWeaver** | 时序关系图、跨 session reconciliation、原始 passage 与结构化事实双通道 | 同时提供时间组织和原文证据，适合构造“当前候选 + 可核查来源” | Graph/Passage 消融支持组件价值；未专门评估生日地址、来源可信度等级或安全行动 |
| **MAGMA** | 不可变时间骨架；时间、因果、实体关系视图分离；查询意图路由 | 可帮助实体连续性和时间顺序检索 | 多图消融支持关系视图互补；没有用户声明/Agent 推断的来源排序，也没有显式事实更新政策 |
| **SimpleMem** | 相对时间规范化、结构化元数据、查询复杂度驱动的多路检索 | 有助于检索计划和时间表达归一化 | 三阶段消融有效；压缩/综合可能丢失罕见历史值，不等价于保留版本与证据来源 |
| **A-MEM** | 动态语义链接、上下文描述与邻近笔记演化 | 可能增加地址相关笔记之间的关联 | LoCoMo 消融支持关联/演化整体有效；主要按相似度检索，可改写旧笔记，没有明确时态状态机 |
| **ARTEM** | 时间/实体/内容分通道、最新事件访问和 vigilance 拒绝 | 可借鉴“只取最新事件”和候选置信阈值 | 合成长文事件任务显示一定能力；没有组件消融，也未做多版本用户事实和来源优先 |
| **MemGuide** | 按意图检索并围绕缺失 slot 筛选记忆 | 仅当地址是当前任务缺失槽位时，可能帮助找到地址值 | 评测是任务型对话；记忆 bank 的 intent 被构造为非冲突，不能据此声称解决同槽位新旧值冲突 |
| **G-Memory** | 多 Agent insight、query、interaction 分层经验 | 可能帮助团队复用协作经验，与用户地址事实问题不直接对应 | 主要在多 Agent QA、具身和规划任务验证；不应作为 AML 地址状态解决方案 |
| **MemOS** | 统一对象、来源/生命周期与自然语言反馈 | 支持把版本与治理纳入系统管理 | 论文/公开版本与商业榜配置分开；没有该场景的完整验证 |
| **Mem0** | 基础管理操作与图关系失效标记 | 能表达更新/冲突处理，图版保留部分关系历史 | 基础删除与图失效不同；没有全套时间/来源/寄送动作证明 |
| **Hindsight** | 时间范围、实体图、事实/意见分型和原文回钻 | 支持来源取证与时间检索 | 多路/反思并不自动解决用户来源优先和精确状态投影 |

### 判断

**没有一篇论文单独、实验证明完整解决这个 bad case。** 其中：

- APEX-MEM 的时态事实/来源证据结构最接近“保存多个地址版本并回答当前或历史地址”；
- PreCoMem 最接近“新说法是真实变化还是低可靠反证”的软管理；
- ReFind 最接近“先忠实保存并搜索原始证据”的轻量 Search 基线；
- MemoTime、MemWeaver、MAGMA 分别提供时间算子、事实—证据双通道、多关系遍历方面的补充。

这些是**针对机制的组合推演**。不能把每篇论文在其他 benchmark 上的结果拼成“组合方案已经有效”的结论。

## 3. 一个可检验的解题流程

针对“现在该把生日卡寄到哪里？”可把原文证据、派生状态与返回证据分开：

### Add：同步保存证据

保留原始轮次与时间、说话人、session/source ID。派生地址记录至少包括：

- 主体与属性（用户 / 地址）；
- 地址值；
- 陈述时间与可能的有效时间范围，二者分开；
- 来源类型（用户直接说、Agent 推断、外部导入）；
- 抽取置信度与原始证据 ID；
- 对其他地址版本的关系（同值支持、显式纠正、可能 supersede、未解决冲突）。

用户说“我搬家了，现在住 Y”时，可以把 Y 作为新候选状态并保留旧地址 X；若只出现 Agent 推断，不能自动覆盖用户陈述。没有可靠的精确搬家日期时，也不应伪造精确的 valid-from 时间。

### Manage：维护候选状态而不删证据

对同一主体/属性聚合同值和冲突值：

- 新的用户明确搬家陈述可支持状态转移，旧地址保留为历史版本；
- 低可靠度抽取或 Agent 推断先进入待确认/低置信状态；
- 来源或时间不足以分辨时，标记 unresolved，不强行二选一；
- 用户明确要求删除时遵循删除语义；保留历史版本不等于可以忽略删除要求。

这一步可分别比较 APEX 式时间版本与 PreCoMem 式可靠性软更新，不要先假设两者组合优于各自方案。

### Search：先识别时间意图，再取来源证据

把问题路由为 current、as-of(2022)、change/history 或 comparison。随后按属性/实体检索并实施相应的时间选择：

- **current：** 返回最近且仍有可靠用户证据支持的当前候选；不是简单对所有记录 recency boost。
- **as-of 2022：** 查询当时有效的地址，并返回对应原文。
- **history/change：** 返回有序版本链及变化依据。
- **来源冲突或时间不明：** 返回并列证据/未解决标记，不静默挑一个值。

可比较两条 Search 路线：ReFind 风格原文 BM25/session 检索，和 APEX/MemoTime 风格结构化时间过滤。若派生状态给出了某个地址，返回包仍应含原始句子、时间戳和来源 ID。

### 交付与行动门槛

AML Search 应只返回最小充分证据包，由固定 Answer/Eval 决定回答。若系统另有真实寄送动作，当前地址的用户证据不够新或来源冲突未解时，应要求确认；这个动作门槛需要单独产品/安全规则，以上记忆论文并未验证它。

## 4. 建议怎样把这个 case 做成实验

把生日地址场景转成小型、可控的 case suite，每个样例同时设置多个时间点与来源：

| 变体 | 历史证据 | 新证据 | 查询 | 主要测项 |
|---|---|---|---|---|
| 明确变化 | 用户 2022 说地址 X | 用户 2024 明确说搬到 Y | 现在地址？/2022 地址？ | Current-State Accuracy / Historical-State Recall |
| 只有重复 | 用户多次说 X | 无新地址 | 现在地址？ | 假更新率 |
| 来源冲突 | 用户说 X | Agent 推断 Y | 现在地址？ | Source Attribution / 错误覆盖率 |
| 不确定抽取 | 用户原话模糊 | 抽取器给出候选 Y | 现在地址？ | 冲突识别与待确认 |
| 明确纠正 | 用户说 X | 用户指出“之前错了，应为 Y” | 地址被何时纠正？ | 显式修正识别与版本链 |
| 历史/当前并问 | 用户 2022 说 X | 用户 2024 说 Y | 搬家前后各是什么？ | 多证据覆盖与时序排序 |

建议比较：当前 EviEpoch；BM25/session-RRF 原文检索；APEX 风格 append-only 时间事实；PreCoMem 风格软状态更新；以及“原文检索 + 轻量状态投影”的组合。所有系统固定 Answer/Eval 和 token/调用预算。

至少报告 Current-State Accuracy、Historical-State Recall、Source Attribution、错误 supersession 率、假更新率、冲突时的错误自信率、Complete Evidence Rate、同步 Add 的 p50/p95 延迟与失败率。这样才能判断方案是在“记住旧地址”“知道现在用哪个”还是仅仅把包含地址的句子找回来。

## 5. 结论

**有可借鉴的解题方法，但目前没有论文证明了完整解法。** 最稳妥的研究假设是：原始来源不可变保存，结构化状态作为可撤销/可重建投影；Manage 对变化与噪声软区分；Search 按问题时间意图选状态并携带证据。是否比 ReFind 式原文搜索、APEX 式时态图或 PreCoMem 式状态维护更好，需要在同一生日地址 case suite 和固定 Answer/Eval 下做消融验证。
